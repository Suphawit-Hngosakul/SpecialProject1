บทที่ 3
วิธีการวิจัย


ในบทนี้นำเสนอวิธีการดำเนินการวิจัยและพัฒนา "ระบบติดตามสภาพแวดล้อมเมืองอัจฉริยะด้วยเทคโนโลยีเซนเซอร์ IoT และการแสดงผลแบบจำลองสามมิติ" โดยอธิบายตั้งแต่ภาพรวมของโครงงาน สถาปัตยกรรมของระบบ การวิเคราะห์ขอบเขตและความต้องการ ประเด็นที่น่าสนใจและสิ่งที่ท้าทายในการพัฒนา วิธีดำเนินงานและการทดสอบ ตลอดจนผลลัพธ์ที่คาดหวังและระบบต้นแบบเบื้องต้น เพื่อให้ผู้อ่านเข้าใจกระบวนการพัฒนาและสามารถทำซ้ำหรือต่อยอดได้


3.1 ภาพรวมของโครงงาน

โครงงานนี้พัฒนาระบบเฝ้าระวังและติดตามสภาพแวดล้อมในเขตเมืองอัจฉริยะ (Smart City Environmental Monitoring) ที่บูรณาการ "อุปกรณ์ตรวจวัดต้นทุนต่ำ (Low-cost Sensor Node)" เข้ากับ "ระบบแสดงผลแบบจำลองสามมิติบนเว็บเบราว์เซอร์ (3D Web Visualization)" เพื่อสื่อสารข้อมูลสภาพแวดล้อมเชิงพื้นที่และเวลา (Spatio-temporal Data) ในรูปแบบที่ผู้ใช้งานทุกระดับสามารถเข้าใจและตัดสินใจได้

ระบบประกอบด้วยสามองค์ประกอบหลัก ได้แก่

1) ส่วนอุปกรณ์ตรวจวัด (Edge Device) — ไมโครคอนโทรลเลอร์ ESP32 ที่บูรณาการเซนเซอร์วัดระดับเสียง (INMP441), อุณหภูมิและความชื้น (DHT22) เข้ากับโมดูล GPS (NEO-8M) และ RTC (DS3231) ในชุดเดียว

2) ระบบจัดเก็บและสื่อสารข้อมูลแบบคู่ขนาน (Dual Logging System) — การบันทึกแบบออฟไลน์ลง SD Card ในรูปแบบไฟล์ CSV ควบคู่กับการส่งข้อมูลแบบเรียลไทม์ขึ้นฐานข้อมูลบนคลาวด์ (InfluxDB on AWS EC2)

3) ระบบแสดงผลสามมิติบนเว็บเบราว์เซอร์ (3D Web Visualization) — เว็บแอปพลิเคชันที่พัฒนาด้วย Three.js / Cesium รองรับการแสดงข้อมูลเซนเซอร์เชิงพื้นที่ในรูปแบบ Heatmap, การจำลองทิศทางและมุมตกกระทบของแสงอาทิตย์ (Sun-Path & Shadow Simulation) และการจำลองระดับน้ำในคลอง (Canal Water Level Simulation)

พื้นที่กรณีศึกษา (Case Study) คือมหาวิทยาลัยธรรมศาสตร์ ศูนย์รังสิต ซึ่งมีทั้งบริเวณอาคารหนาแน่นและคลองภายในพื้นที่ ทำให้เหมาะสมต่อการทดสอบทั้งมิติด้านการตรวจวัดสภาพแวดล้อม (เสียง อุณหภูมิ ความชื้น พิกัด) และมิติด้านการจำลองทางกายภาพ (แสงเงา และระดับน้ำ)


3.2 สถาปัตยกรรมของระบบ

สถาปัตยกรรมของระบบออกแบบตามแนวคิด IoT Reference Architecture แบ่งเป็นสามชั้นหลัก ได้แก่ Perception Layer (เซนเซอร์), Network & Storage Layer (เครือข่ายและฐานข้อมูล) และ Application Layer (การแสดงผลและการจำลอง) โดยมีแผนภาพในรูปที่ 3.1


3.2.1 สถาปัตยกรรมระดับระบบ (System-Level Architecture)

ระบบทำงานในลักษณะ end-to-end ตั้งแต่การอ่านค่าจากเซนเซอร์ในภาคสนาม ส่งผ่านเครือข่าย Wi-Fi ขึ้นสู่ฐานข้อมูลบนคลาวด์ จนถึงการแสดงผลบนเว็บเบราว์เซอร์ในรูปแบบสามมิติ โดยมีองค์ประกอบในแต่ละชั้นดังนี้


3.2.1.1 ส่วนอุปกรณ์ตรวจวัด (Edge Device)

อุปกรณ์ตรวจวัดสร้างขึ้นจาก ESP32 ที่บูรณาการเซนเซอร์ทั้งหมดไว้ในชุดเดียว ทำหน้าที่ (1) อ่านค่าจากเซนเซอร์อย่างต่อเนื่อง (2) คำนวณค่า SPL จากสัญญาณดิจิทัล I2S (3) ผูกข้อมูลทุกชุดกับพิกัด GPS และ timestamp จาก DS3231 RTC ที่ sync กับ NTP (4) บันทึกลง SD Card และ (5) ส่งข้อมูลขึ้นคลาวด์ในเวลาเดียวกัน หน้าจอ OLED แสดงสถานะการทำงานของอุปกรณ์ในภาคสนาม รายละเอียดของการเชื่อมต่อฮาร์ดแวร์ดูในหัวข้อ 3.2.2.1


3.2.1.2 ส่วน Cloud Backend

ส่วนคลาวด์มีแผนการติดตั้งบน Amazon EC2 (Ubuntu) ใน Region ap-southeast-1 โดยจะรัน Docker Containers สองตัว ได้แก่ (1) InfluxDB (port 8086) ทำหน้าที่เป็น Time-Series Database สำหรับเก็บข้อมูลเซนเซอร์ที่ส่งมาจากอุปกรณ์ตรวจวัด และ (2) Grafana (port 3000) สำหรับ Dashboard ภายในระหว่างการพัฒนาและการตรวจสอบข้อมูล EC2 instance จะกำหนด Elastic IP เพื่อให้อุปกรณ์ภาคสนามอ้างอิงปลายทางได้อย่างคงที่ ส่วน Security Group จะเปิดเฉพาะพอร์ตที่จำเป็น (22 สำหรับ SSH, 8086 สำหรับ InfluxDB และ 3000 สำหรับ Grafana)

ในด้านการสื่อสารระหว่างอุปกรณ์ตรวจวัดกับคลาวด์ ESP32 จะส่งข้อมูลขึ้น InfluxDB ผ่าน HTTP Line Protocol โดยใช้ Token-based Authentication และมีกลไก Exponential Backoff เมื่อการเชื่อมต่อล้มเหลว รายละเอียดของแผนการติดตั้งและการกำหนดค่าทั้งหมดจะดำเนินการในเฟสที่ 3 ของแผนการพัฒนา (หัวข้อ 3.5.1)


3.2.1.3 ส่วน 3D Web Visualization

เว็บแอปพลิเคชันพัฒนาด้วย Three.js หรือ Cesium บน WebGL ทำหน้าที่ดึงข้อมูลจาก InfluxDB ผ่าน Flux Query API แล้วแสดงผลในรูปแบบสามมิติ ครอบคลุม

1) Heatmap เชิงพื้นที่ของค่า SPL และอุณหภูมิตามพิกัด GPS

2) Sun-Path & Shadow Simulation จำลองทิศทางและมุมตกกระทบของแสงอาทิตย์ตามวันและเวลา โดยใช้ไลบรารี SunCalc.js ในการคำนวณตำแหน่งดวงอาทิตย์ และเทคนิค Shadow Mapping ของ Three.js

3) Canal Water Level Simulation จำลองการเปลี่ยนแปลงของระดับน้ำในคลอง

โครงสร้างภายในของชั้นนี้แบ่งเป็น Presentation Layer (UI / Time Slider / Info Panel), Simulation Layer (Sun-Path & Shadow / Water Level / Heatmap), Scene Layer (3D models, terrain, markers, lights), 3D Library Layer (Three.js / Cesium / SunCalc.js) และ Runtime Layer (WebGL / JavaScript) ตามลำดับ เว็บแอปดึงข้อมูลจาก InfluxDB ผ่าน Flux Query API แล้ว render บน WebGL canvas โดยอัปเดตทุก 5–10 วินาที


3.2.2 สถาปัตยกรรมระดับอุปกรณ์ (Device-Level Architecture)


3.2.2.1 ฮาร์ดแวร์และการเชื่อมต่อ (Hardware Interface)

ฮาร์ดแวร์ทั้งหมดเชื่อมต่อกับ ESP32 ผ่านโปรโตคอลที่เหมาะสมตามคุณสมบัติของอุปกรณ์ ดังตารางที่ 3.1

ตารางที่ 3.1 อุปกรณ์ฮาร์ดแวร์และการเชื่อมต่อ

1	ไมโครคอนโทรลเลอร์	ESP32 DevKit v1 (Dual-core 240 MHz, 520 KB SRAM)	—	—
2	ไมโครโฟน MEMS	INMP441 (24-bit, SNR 61 dBA)	I2S	SCK=26, WS=25, SD=33

3.2.2.2 โครงสร้างซอฟต์แวร์แบบ Multi-task บน FreeRTOS

ซอฟต์แวร์บน ESP32 พัฒนาด้วยภาษา C/C++ ภายใต้ ESP32 Arduino Core และระบบปฏิบัติการ FreeRTOS ซึ่งรองรับการทำงานแบบ Preemptive Multitasking โดยแยก task ตามหน้าที่และจัดสรร core ที่เหมาะสม ดังตารางที่ 3.2

ตารางที่ 3.2 รายละเอียดของ FreeRTOS Tasks

Task	Core	Priority	Stack	คาบเวลา	หน้าที่
micTask	1	2	4 KB	ต่อเนื่อง (I2S DMA)	อ่านสัญญาณ I2S จาก INMP441 ส่งเข้า readyQueue
sdProcessTask	0	1	8 KB	event-driven	รับ block เสียง คำนวณ SPL (RMS + EMA) และเขียน CSV
gpsTask	0	1	4 KB	continuous parse	parse NMEA จาก UART2 และ update พิกัด GPS
dhtTask	0	1	4 KB	2,000 ms	อ่าน DHT22 อุณหภูมิและความชื้น
oledTask	0	1	4 KB	500 ms	refresh OLED 5 บรรทัด
influxTask	0	1	8 KB	1,000 ms (batch 5)	สร้าง Line Protocol และ POST ไปยัง InfluxDB

การ pin micTask ไว้ที่ Core 1 ป้องกันไม่ให้การอ่านสัญญาณเสียงถูกรบกวนจาก task ที่เกี่ยวข้องกับเครือข่าย (ซึ่งทำงานบน Core 0 ตามค่าเริ่มต้นของ ESP32 Arduino Core) จึงรับประกันความเป็นเรียลไทม์ของการสุ่มสัญญาณเสียงที่ 16 kHz โดยไม่เกิด packet loss


3.2.2.3 กลไก Synchronization (Queue + Mutex)

ระบบใช้ FreeRTOS Synchronization Primitives สองชนิดหลัก ได้แก่

1) Queue — readyQueue ใช้ส่งข้อมูล AudioBlock จาก micTask (producer) ไปยัง sdProcessTask (consumer) แบบ FIFO ซึ่งเป็น pattern Producer-Consumer ที่แยกการอ่าน I/O ออกจากการประมวลผล ทำให้การอ่านสัญญาณเสียงไม่ถูก block แม้การเขียน SD จะใช้เวลานานก็ตาม

2) Mutex — ใช้ป้องกัน Race Condition เมื่อมีหลาย task เข้าถึงทรัพยากรร่วมพร้อมกัน รายละเอียดดังตารางที่ 3.3

ตารางที่ 3.3 Mutex และทรัพยากรร่วมที่ป้องกัน

Mutex	ทรัพยากรที่ป้องกัน	Task ที่ใช้งาน
sdMutex	SD_MMC read/write	sdProcessTask
oledMutex	display* variables	oledTask + sensor tasks
gpsMutex	gps* variables	gpsTask (write) + influxTask/oledTask (read)
dhtMutex	dhtTemp, dhtHumidity, dhtValid	dhtTask (write) + readers
wireMutex	I2C bus (DS3231 + OLED)	sensor + OLED + RTC ทุก task
wifiMutex	WiFi.begin() reconnect	influxTask (และ task อื่นในอนาคต)

การเรียกใช้ Mutex ใช้รูปแบบ Timeout-based Acquisition ผ่าน xSemaphoreTake(mutex, timeout) ที่ return boolean เพื่อแยกกรณี "ได้ mutex" จาก "timeout" ทำให้ฟังก์ชันเช่น readDhtSafe() สามารถคืนค่า false เมื่อ timeout ได้โดยไม่ block ค้าง สอดคล้องกับกลไก Watchdog Timer ที่กำหนดเวลาตอบสนองสูงสุดของแต่ละ task ไว้ 10 วินาที


3.2.3 การไหลของข้อมูล (Data Flow)

ข้อมูลในระบบไหลตามลำดับดังนี้

1) ไมโครโฟน INMP441 ส่งสัญญาณ PCM ผ่าน I2S DMA ไปยัง micTask

2) micTask แพ็คเป็น AudioBlock ส่งเข้า readyQueue แล้วเข้าสู่ sdProcessTask

3) sdProcessTask คำนวณ RMS เป็นช่วง ๆ และ smooth ด้วย EMA ออกมาเป็นค่า currentSPL

4) เซนเซอร์อื่น (DHT22, GPS) อ่านโดย task เฉพาะ แล้ว update sensor globals

5) ทุก 1 วินาที sdProcessTask รวมข้อมูลจาก globals กับ RTC แล้วเขียน CSV ลง SD Card

6) ทุก 1 วินาที influxTask อ่าน snapshot ผ่าน readXxxSafe() สร้าง Line Protocol และ POST ขึ้น InfluxDB (มี Exponential Backoff เมื่อ fail)

7) oledTask แสดงสรุปบน OLED ทุก 500 ms

ลำดับการทำงานในหนึ่งรอบการวัด (Sequence of One Measurement Cycle) แสดงในรูปที่ 3.2

NFR-03	Latency ของระบบ	ข้อมูลในเว็บแอปล่าช้าจากข้อมูลจริงไม่เกิน 10 วินาที
NFR-04	ความถูกต้องของ Timestamp	คลาดเคลื่อนจากเวลาจริงไม่เกิน 1 วินาที (หลัง NTP sync)
NFR-05	ต้นทุน (Cost)	ต้นทุนฮาร์ดแวร์ต่อ Node ≤ 2,500 บาท
NFR-06	Maintainability	โครงสร้างโค้ดแยกตามฟังก์ชัน รองรับการเพิ่ม/ลดเซนเซอร์ได้โดยไม่กระทบส่วนอื่น
NFR-07	Frame Rate ของ 3D	เว็บแอปแสดงผลที่ ≥ 30 fps บน browser ที่รองรับ WebGL 2.0


3.3.3 ขอบเขตและข้อจำกัด (Scope & Constraints)

ขอบเขตของระบบ

- ครอบคลุมการวัดเสียง อุณหภูมิ ความชื้น และพิกัด GPS เท่านั้น (ไม่รวม PM 2.5, CO₂, แสง, UV)
- ใช้ Wi-Fi 2.4 GHz เป็นเครือข่ายเดียว (ไม่รองรับ Cellular หรือ LoRa)
- พื้นที่กรณีศึกษาคือมหาวิทยาลัยธรรมศาสตร์ ศูนย์รังสิต
- ระยะเวลาเก็บข้อมูลทดสอบประมาณ 4 สัปดาห์

ข้อจำกัด

- ไมโครโฟน INMP441 เป็นระดับ Consumer-grade ไม่ใช่เครื่องมือมาตรฐาน (Scientific/Industrial-grade)
- DHT22 มีความละเอียด 0.1°C / 0.1%RH ซึ่งเพียงพอสำหรับการวิเคราะห์แนวโน้ม แต่ไม่เทียบกับเครื่องมือห้องปฏิบัติการ
- GPS NEO-8M ต้องการ Clear Line of Sight จึงทำงานได้ดี
- การจำลองแสงเงาและน้ำในคลองเป็นการแสดงผลเชิงทัศนภาพ (Visualization) ไม่ใช่การจำลองพลศาสตร์ของของไหล (Fluid Dynamics)


3.4 ประเด็นที่น่าสนใจและสิ่งที่ท้าทาย

การพัฒนาระบบที่บูรณาการฮาร์ดแวร์ เครือข่าย ฐานข้อมูล และการแสดงผลสามมิติเข้าด้วยกัน มีประเด็นทางเทคนิคที่ท้าทายหลายด้าน ผู้จัดทำได้วิเคราะห์ประเด็นเหล่านี้และออกแบบกลไกรับมือไว้ในระบบดังนี้


3.4.1 ความท้าทายด้านการประมวลผลสัญญาณเสียง


3.4.1.1 การจัดการ I2S Buffer และ DMA Latency

ESP32 ใช้ DMA (Direct Memory Access) ในการอ่านข้อมูลจาก I2S peripheral ทำให้ลดภาระของ CPU แต่ขนาดของ DMA buffer และจำนวน descriptor ต้องเลือกให้สมดุล หาก buffer เล็กเกินไปจะเกิดสภาวะ overrun (ข้อมูลใหม่เขียนทับเก่าก่อนถูกอ่าน) แต่ถ้าใหญ่เกินไปจะเพิ่ม latency ของการคำนวณ SPL โครงงานนี้ใช้

- Buffer length (BUFFER_LEN): 512 samples ต่อ block (~32 ms ที่ 16 kHz)
- Audio pool size (AUDIO_POOL_SIZE): 8 blocks (~256 ms ของ buffered audio)
- Sample rate (SAMPLE_RATE): 16,000 Hz, 16-bit mono

ค่าเหล่านี้ทำให้มีเวลา ~256 ms ในการประมวลผลก่อนเกิด overrun ซึ่งเพียงพอแม้ในกรณีที่ task อื่นใช้ CPU ชั่วคราว


3.4.1.2 การ Calibrate ไมโครโฟน INMP441

ค่า SPL ที่คำนวณจากสัญญาณดิจิทัลของ INMP441 อยู่ในสเกล dBFS (decibels relative to full scale) ซึ่งเป็นสเกลของสัญญาณดิจิทัลเทียบกับค่าเต็มสเกลของ ADC ภายในไมโครโฟน จึงต้องบวกค่า offset (MIC_OFFSET_DB) เพื่อแปลงให้ตรงกับสเกล dB SPL ในทางกายภาพ ค่า offset นี้ขึ้นอยู่กับ sensitivity ของไมโครโฟนแต่ละตัวและสภาพการติดตั้ง ทำให้ไม่สามารถใช้ค่าจาก datasheet โดยตรงได้อย่างแม่นยำ

ในระยะปัจจุบันของการพัฒนา ระบบใช้ค่า MIC_OFFSET_DB = 115.0 เป็นค่าเริ่มต้นที่ประมาณการจาก datasheet ของ INMP441 (sensitivity −26 dBFS @ 94 dB SPL) ค่าจริงจะถูกปรับให้แม่นยำขึ้นในขั้นตอน Calibration ซึ่งมีรายละเอียดในหัวข้อ 3.5.2


3.4.2 ความท้าทายด้านความน่าเชื่อถือของระบบฝังตัวและเครือข่าย


3.4.2.1 Watchdog Timer และการ Recover อัตโนมัติ

ทุก task ของระบบลงทะเบียนกับ Task Watchdog Timer (TWDT) ของ ESP-IDF ผ่าน esp_task_wdt_add() และต้อง feed watchdog ผ่าน esp_task_wdt_reset() ภายในระยะเวลา WDT_TIMEOUT_S = 10 วินาที หาก task ใด timeout ระบบจะ panic และ reboot อัตโนมัติ ป้องกันการ hang แบบไม่รู้ตัว นอกจากนี้ยังมีกลไกย่อยอีกสองส่วน

1) I2S Error Recovery — เมื่อ i2s_read() เกิด error ติดต่อกัน (consecutive errors) ครบ 50 ครั้ง ระบบจะเรียก i2s_reinstall() เพื่อ uninstall และ install driver ใหม่ โดยไม่ต้อง reboot อุปกรณ์ทั้งระบบ

2) SD Card Health Check — เมื่อ SD Card write error ครบ 10 ครั้ง ระบบจะตั้งค่า sdHealthy = false และหยุดบันทึกชั่วคราวเพื่อป้องกัน filesystem เสียหาย พร้อมรายงานสถานะบน OLED


3.4.2.2 Exponential Backoff สำหรับการส่งข้อมูลขึ้นคลาวด์

เมื่อ Wi-Fi หรือ InfluxDB ไม่ตอบสนอง ระบบใช้ Exponential Backoff ผ่าน Backoff struct ที่ปรับระยะเวลา retry แบบทวีคูณ ตามสมการ

delay = clamp(BASE_MS × MULTIPLIER^n, BASE_MS, CAP_MS)

โดยที่
BASE_MS = 1,500 ms
MULTIPLIER = 2.0
CAP_MS = 60,000 ms

เริ่มจาก retry ครั้งแรกที่ 1.5 วินาที, 3 วินาที, 6 วินาที, 12 วินาที, 24 วินาที, 48 วินาที จนถึงเพดาน 60 วินาที พร้อม reset เมื่อส่งสำเร็จ ลดภาระทั้งบน ESP32 และ EC2 และป้องกัน packet loss จากการ retry ถี่เกินไปในสภาพเครือข่ายไม่เสถียร


3.4.2.3 การจัดการ Race Condition ของ Wi-Fi

ในระบบที่หลาย task อาจเรียก WiFi.begin() พร้อมกัน (เช่น influxTask และ task ส่งข้อมูลในอนาคต) อาจทำให้ ESP32 hang ระบบจึงใช้ wifiMutex ร่วมกับ Double-Check Pattern คือตรวจสถานะ WiFi.status() == WL_CONNECTED ทั้งก่อนและหลังการ acquire mutex เพื่อหลีกเลี่ยงการ reconnect ซ้ำซ้อน


3.4.3 ความท้าทายด้านการแสดงผลสามมิติ


3.4.3.1 ประสิทธิภาพการเรนเดอร์บนเว็บเบราว์เซอร์

WebGL บนเบราว์เซอร์มีข้อจำกัดด้านจำนวน vertex และ texture memory การโหลดโมเดลอาคารทั้งพื้นที่กรณีศึกษาในความละเอียดสูงพร้อมกันอาจทำให้ frame rate ลดลงต่ำกว่าเกณฑ์ NFR-07 (≥ 30 fps) เทคนิคที่ใช้แก้ปัญหานี้ ได้แก่

- Level of Detail (LOD) — โหลดโมเดลความละเอียดต่ำเมื่อกล้องอยู่ไกล
- Instanced Geometry — สำหรับอาคารที่มีรูปทรงซ้ำ
- Frustum Culling — render เฉพาะวัตถุที่อยู่ในมุมมองของกล้อง


3.4.3.2 ความสมจริงของการจำลองตำแหน่งดวงอาทิตย์และเงา

การคำนวณตำแหน่งดวงอาทิตย์อาศัยพิกัด latitude / longitude ของพื้นที่กรณีศึกษา และเวลาท้องถิ่น แปลงเป็นมุมเงย (Altitude) และมุมแอซิมุท (Azimuth) ผ่านไลบรารี SunCalc.js แล้วใช้กำหนดทิศทางของ DirectionalLight ใน Three.js ร่วมกับเทคนิค Shadow Mapping เพื่อสร้างเงาที่ตกกระทบบนอาคารและพื้นผิวเมือง ทั้งนี้แบบจำลองนี้ไม่ได้พิจารณาเมฆหรือสภาพอากาศที่หักเหหรือกระจายแสง จึงเป็นการประมาณการในสภาพท้องฟ้าโปร่ง


3.4.4 ความท้าทายด้านการจัดการ Memory และ Heap Fragmentation

การทำงานต่อเนื่องเป็นเวลานานบนระบบฝังตัวมีแนวโน้มที่จะเกิด heap fragmentation จากการ allocate/free memory ซ้ำ ๆ ผู้จัดทำลดปัญหานี้โดย

- ใช้ LOG() macro ที่อาศัย buffer แบบ static และไม่มีการ allocate heap ในขั้นตอนการพิมพ์ log
- ใช้ static local variables สำหรับ buffer ที่มีอายุการใช้งานยาว เช่น audioFile, wavFileName, splInitialized ในไฟล์ sd_logger.cpp
- หลีกเลี่ยง String object ของ Arduino ใน critical path ที่ทำงานบ่อย

3.5.2 แผนการ Calibrate ไมโครโฟน

การ Calibrate ไมโครโฟน INMP441 เป็นขั้นตอนสำคัญที่ทำให้ค่า SPL ที่อ่านได้สอดคล้องกับเครื่องวัดเสียงมาตรฐาน ขั้นตอนที่จะดำเนินการมีดังนี้

อุปกรณ์ที่ใช้

- เครื่องวัดเสียงมาตรฐาน (Sound Level Meter Class 2 ตามมาตรฐาน IEC 61672) เป็นเครื่องอ้างอิง
- Speaker สำหรับปล่อยสัญญาณเสียงอ้างอิง (Pink Noise)
- สภาพแวดล้อมที่ควบคุมเสียงรบกวน (ห้องปิด, เสียงรบกวนพื้นหลัง < 30 dB)
- คอมพิวเตอร์สำหรับบันทึกข้อมูลจาก ESP32 และเครื่องวัดมาตรฐาน

ขั้นตอน

1) วาง INMP441 และเครื่องวัดมาตรฐานคู่กันในตำแหน่งที่ระยะห่างจาก speaker เท่ากัน

2) ปล่อยสัญญาณ Pink Noise ที่ระดับเสียงคงที่หลายระดับ ได้แก่ 50, 60, 70, 80 และ 90 dB (วัดด้วยเครื่องมาตรฐาน)

3) ในแต่ละระดับ บันทึกค่าเฉลี่ยจาก ESP32 (เป็นค่า dBFS ก่อนบวก offset) และค่าจากเครื่องมาตรฐานเป็นเวลา 60 วินาที

4) คำนวณค่า MIC_OFFSET_DB ที่ทำให้ Mean Absolute Error (MAE) ระหว่างค่าจาก ESP32 (หลังบวก offset) กับเครื่องมาตรฐานต่ำที่สุด ตามสมการ

MIC_OFFSET_DB = argmin_c ของผลรวม |L_ESP,i + c − L_ref,i| สำหรับ i = 1 ถึง N

5) นำค่า offset ที่ได้ไปปรับใน config.h แล้ว flash firmware ใหม่

6) ทดสอบยืนยัน (Validation) ด้วยระดับเสียงชุดใหม่ที่ไม่ได้ใช้ในข้อ 2 (เช่น 55, 65, 75 dB) เพื่อประเมินความคลาดเคลื่อนตามเป้าหมาย NFR-02 (±3 dB)

3.6 ผลลัพธ์ที่คาดหวัง

ผู้จัดทำคาดหวังว่าระบบที่พัฒนาขึ้นจะให้ผลลัพธ์ดังนี้

1) อุปกรณ์ตรวจวัดต้นทุนต่ำ (Sensor Node) ที่บูรณาการเซนเซอร์ SPL, DHT22, GPS, RTC, OLED และ SD Card บน ESP32 ในชุดเดียว สามารถใช้งานในภาคสนามได้จริง

2) ฐานข้อมูลแบบคู่ขนาน ประกอบด้วยไฟล์ CSV บน SD Card สำหรับข้อมูลย้อนหลังแบบสมบูรณ์ และ InfluxDB บนคลาวด์สำหรับข้อมูลเรียลไทม์

3) เว็บแอปพลิเคชันแสดงผลสามมิติ ที่สามารถแสดงข้อมูลเซนเซอร์เชิงพื้นที่และเวลา รวมถึงรองรับ Sun-Path & Shadow Simulation และ Canal Water Level Simulation

4) เอกสารผลการ Calibration ของไมโครโฟน INMP441 ที่เทียบกับเครื่องวัดเสียงมาตรฐาน พร้อมค่า MIC_OFFSET_DB ที่ปรับแล้ว

5) รายงานการประเมินประสิทธิภาพ ในพื้นที่กรณีศึกษามหาวิทยาลัยธรรมศาสตร์ ศูนย์รังสิต ครอบคลุมความแม่นยำของข้อมูล เสถียรภาพของระบบ และประสิทธิภาพการแสดงผลตามตัวชี้วัดในหัวข้อ 3.5.3

3.7 ระบบต้นแบบและผลลัพธ์เบื้องต้น

ในช่วงต้นของการพัฒนา ผู้จัดทำได้สร้างระบบต้นแบบและทดสอบเบื้องต้นในห้องปฏิบัติการและบริเวณรอบที่อยู่อาศัย โดยมีผลลัพธ์เบื้องต้นในแต่ละด้านดังนี้

ด้านการตรวจวัด

- ESP32 อ่านสัญญาณ I2S จาก INMP441 ได้อย่างต่อเนื่องที่ sample rate 16 kHz โดยไม่เกิด packet loss
- ค่า SPL ที่คำนวณจาก RMS + EMA smoothing มีความเสถียร เปลี่ยนแปลงตามระดับเสียงในสภาพแวดล้อม
- ในขั้นต้นใช้ค่า MIC_OFFSET_DB = 115.0 ตามที่ประมาณจาก datasheet ของ INMP441 ซึ่งให้ค่า SPL ที่อยู่ในช่วงที่สมเหตุสมผลและตอบสนองต่อระดับเสียงที่เปลี่ยนแปลงได้อย่างเสถียร อย่างไรก็ตามการ Calibrate เทียบกับเครื่องวัดเสียงมาตรฐานเพื่อปรับค่า offset ให้แม่นยำตามขั้นตอนในหัวข้อ 3.5.2 ยังคงเป็นขั้นตอนที่ต้องดำเนินการในการทดสอบภาคสนามต่อไป
- DHT22 ให้ค่าอุณหภูมิและความชื้นที่สอดคล้องกับเครื่องวัดอ้างอิงในห้อง
- GPS NEO-8M สามารถระบุพิกัดในพื้นที่กลางแจ้งได้ภายในเวลาประมาณ 30 วินาที โดยมีค่า HDOP ต่ำกว่า 2 ในสภาพท้องฟ้าโปร่ง

ด้านการจัดเก็บข้อมูลแบบคู่ขนาน

- ไฟล์ CSV บน SD Card ถูกเขียนทุก 1 วินาที โดยมี timestamp จาก DS3231 และพิกัด GPS กำกับ
- โมดูลส่งข้อมูลขึ้น InfluxDB ใน firmware ทำงานสมบูรณ์ในการทดสอบกับ InfluxDB ที่ run บนเครื่องท้องถิ่น (Local) โดยส่งแบบ batch ทุก 1 วินาที ทั้งนี้ระบบจะถูกย้ายไปยัง InfluxDB บน Amazon EC2 ในเฟสที่ 3 ของแผนการพัฒนา
- เมื่อ Wi-Fi ขาดการเชื่อมต่อ Exponential Backoff ทำงานตามที่ออกแบบไว้ และข้อมูลใน SD Card ยังคงต่อเนื่องไม่ขาดตอน

ด้านความเสถียร

- ทดสอบเดินเครื่องต่อเนื่องในห้องปฏิบัติการเบื้องต้น ไม่พบการ reboot โดย Watchdog Timer
- กลไก I2S Error Recovery และ SD Health Check ทำงานได้ถูกต้องเมื่อจำลองสภาวะ error (ถอด/เสียบ SD Card ระหว่างทำงาน)

ด้านการแสดงผล

- OLED แสดงข้อมูล 5 บรรทัด ได้แก่ เวลา, SPL และสถานะการบันทึก, แสง+UV (จะเปลี่ยนเป็นบรรทัดอื่นในเวอร์ชันถัดไป), อุณหภูมิและความชื้น, และสถานะ GPS
- Grafana Dashboard เบื้องต้น (ใช้ระหว่างพัฒนา) แสดง time-series ของ SPL, อุณหภูมิ, ความชื้น และตำแหน่ง GPS บน Geomap ได้ตามที่คาดหวัง
- เว็บแอปพลิเคชัน 3D Visualization ในระยะเริ่มต้นสามารถ render โมเดลอาคารและคำนวณตำแหน่งดวงอาทิตย์ตามวันเวลาที่กำหนดได้ การพัฒนาส่วนของ Heatmap และ Canal Water Level Simulation อยู่ในขั้นตอนถัดไป

ผลลัพธ์เบื้องต้นเหล่านี้แสดงให้เห็นว่าสถาปัตยกรรมและการออกแบบที่เลือกใช้สามารถบรรลุวัตถุประสงค์ของโครงงานได้ในระดับที่น่าพอใจ และจะถูกพัฒนาเพิ่มเติมในขั้นต่อไป ได้แก่ การ Calibrate ไมโครโฟนกับเครื่องวัดมาตรฐาน, การติดตั้งทดสอบจริงในพื้นที่กรณีศึกษามหาวิทยาลัยธรรมศาสตร์ ศูนย์รังสิต, การประเมินความเสถียรในระยะยาว (≥ 7 วัน), การพัฒนาฟีเจอร์ Sun-Path & Shadow Simulation และ Canal Water Level Simulation บนเว็บแอปพลิเคชันให้สมบูรณ์ และการเก็บข้อมูลตามตัวชี้วัดในหัวข้อ 3.5.3 เพื่อสรุปในบทที่ 4 และ 5 ต่อไป
